# fsnt-torrent-blocker

Детектор торрент-трафика для [Remnawave Node](https://remna.st/), который ловит то, что пропускает штатный Torrent Blocker. Работает двумя сигналами:

1. **Веер по логу** — зашифрованные пиры (MSE/PE) на случайных портах, у которых нет сигнатуры: их выдаёт поведение (много адресов на разных портах за короткое окно).
2. **btguard** — nft-дроп UDP-контрплана торрента (DHT, uTP-хендшейк, connect к UDP-трекеру) по строгим сигнатурам, с привязкой каждого дропа к клиенту.

Обе находки уходят в тот же внутренний вебхук ноды, поэтому бан в nftables, уведомление в Telegram и вебхук `torrent_blocker.report` работают как для нативных срабатываний. Ставится одной командой — детектор и nft-правила вместе.

```bash
curl -fsSL https://raw.githubusercontent.com/forestsnet/torrent-blocker/main/install.sh | sudo bash
```

---

## Зачем

Штатный Torrent Blocker опирается на сниффер xray, а документация Remnawave прямо оговаривает, что xray видит лишь 10–30% торрент-трафика. Мимо проходит:

- **пиры под MSE/PE-шифрованием** — в qBittorrent и большинстве клиентов оно включено по умолчанию, открытого рукопожатия `BitTorrent protocol` в TCP нет;
- **DHT** — отдельного сниффера для него в xray нет вовсе;
- **правила по портам и доменам трекеров** — пиры ходят по голым IP на случайных высоких портах, ни `geosite:category-public-tracker`, ни список портов их не ловят.

На живой ноде клиент с активной раздачей за 75 секунд открыл соединения к **102 адресам на 91 разном порту** — и всё ушло в `DIRECT`, штатный блокер не сработал ни разу.

## Как это работает

### Сигнал 1 — веер (шифрованные пиры)

Детектор читает access-лог xray и для каждого пользователя считает число различных адресов и портов назначения за скользящее окно (по умолчанию 60 секунд).

> Торрент-клиент открывает соединения к десяткам пиров, у каждого пира свой порт. Такого веера не даёт ни браузер, ни мессенджер, ни звонок: у обычного пользователя за минуту набирается до двух десятков адресов на высоких портах, у торрентящего — 50–150.

Соединения по доменам, к частным адресам и на порты веба, DNS, почты, мессенджеров и STUN/TURN в подсчёт не идут. Так ловятся зашифрованные MSE/PE-пиры, у которых нет сигнатуры.

### Сигнал 2 — btguard (UDP-контрплан)

Отдельная nft-таблица `btguard` дропает на выходе то, что сниффер xray по UDP пропускает: **DHT** (BEP 5), **uTP-хендшейк** (BEP 29) и **connect к UDP-трекеру** (BEP 15) — по строгим сигнатурам (полям заголовков, а не префиксам). Каждый дроп попадает в kernel-лог с адресом пира. Детектор читает этот лог и восстанавливает клиента: тот же поток есть в access-логе как `udp:<пир>:<порт> email:<клиент>`, так что по `пир:порт` находится, кто именно торрентил. Дальше — тот же бан.

Сигнатуры ужесточены по логике форка [Jolymmiles/Xray-core](https://github.com/Jolymmiles/Xray-core) (`dht.go`, `udp_tracker.go`, `SniffUTP`). Это критично: наивный uTP-матч `0x4100` ловит TURN/WebRTC-медиа (в замере 176 ложных пакетов за 90с), строгий по полям ST_SYN — ноль.

### Что дальше

Когда сработал любой из сигналов, детектор отправляет отчёт во внутренний вебхук ноды — тот же, куда отчитывается сам xray. Дальше нода работает сама:

1. банит IP клиента в nftables на `blockDuration` с учётом `ignoreLists`;
2. рвёт его текущие соединения;
3. передаёт отчёт в панель, а панель — в Telegram и вебхук `torrent_blocker.report`.

Адрес вебхука (сокет и токен) детектор каждый раз берёт из работающего конфига xray, поэтому переживает перезапуски ноды без донастройки. Поддерживаются оба поколения ноды — с абстрактным сокетом (`@rwint-…`) и с файловым (`/run/remnawave-internal-….sock`). Путь к access-логу берётся из `log.access`; если там пусто, детектор перебирает `/var/log/remnanode/…` и `/var/log/xray/current` и выбирает файл, где реально есть строки подключений.

## Требования

- Remnawave Node **2.7.0+**, плагин Torrent Blocker включён (нода с `cap_add: NET_ADMIN`)
- access-лог xray не выключен: `log.access` ≠ `"none"`
- systemd, root, python3 **3.6+** (если python3 нет, установщик поставит его сам — стандартной библиотеки достаточно, внешних зависимостей нет)

## Установка

```bash
curl -fsSL https://raw.githubusercontent.com/forestsnet/torrent-blocker/main/install.sh | sudo bash
```

Установщик кладёт детектор в `/usr/local/sbin/fsnt-torrent-blocker`, настройки в `/etc/default/fsnt-torrent-blocker`, юнит `fsnt-torrent-blocker.service`, а также nft-правила `btguard` (`/etc/nftables.d/btguard.nft` + `btguard.service`, oneshot). Флаг `--no-btguard` ставит только веерный детект по логу. Перед включением он прогоняет **selftest**: находит xray, вебхук и лог, отправляет пробный отчёт без пользователя (нода проверяет формат, но ничего не банит) и заведомо битый отчёт (нода должна его отвергнуть). Если что-то не сходится — сервис не включается. Повторный запуск обновляет детектор и сохраняет настройки.

**Сначала посмотреть, кого поймает, без банов:**

```bash
curl -fsSL https://raw.githubusercontent.com/forestsnet/torrent-blocker/main/install.sh | sudo bash -s -- --dry-run
journalctl -u fsnt-torrent-blocker -f
```

**Перевести в боевой режим:**

```bash
curl -fsSL https://raw.githubusercontent.com/forestsnet/torrent-blocker/main/install.sh | sudo bash -s -- --live
```

**Задать пороги сразу при установке:**

```bash
curl -fsSL …/install.sh | sudo bash -s -- --min-hosts 30 --min-ports 25 --window 90
```

Исключить легальный сервис на своих портах (например, локальный порт ноды, который бьёт по многим адресам):

```bash
curl -fsSL …/install.sh | sudo bash -s -- --ignore-ports "7680,1010"
```

**На все свои узлы со своей машины** (доступ сервера к GitHub не нужен — детектор вшит в `install.sh`):

```bash
for h in 10.0.0.1 10.0.0.2 10.0.0.3; do ssh deploy@$h 'sudo bash -s' < install.sh; done
```

## Настройка

Пороги задаются флагами при установке **и** правятся потом в `/etc/default/fsnt-torrent-blocker` (после правки — `systemctl restart fsnt-torrent-blocker`). Флаг и переменная конфига — одно и то же:

| Флаг установки | Переменная | По умолчанию | Что делает |
|---|---|---|---|
| `--dry-run` / `--live` | `FTB_DRY_RUN` | `0` | `1` — только писать находки в журнал, в ноду не отправлять |
| `--no-btguard` | `FTB_BTGUARD` | `auto` | `auto` — включить btguard-корреляцию, если nft-таблица есть; `off` — только веер; `on` — форс |
| `--window N` | `FTB_WINDOW` | `60` | окно наблюдения, секунд |
| `--min-hosts N` | `FTB_MIN_HOSTS` | `25` | порог: разных адресов назначения за окно |
| `--min-ports N` | `FTB_MIN_PORTS` | `20` | порог: разных портов назначения за окно (нужны **оба** условия) |
| `--cooldown N` | `FTB_COOLDOWN` | `300` | не отправлять повторный отчёт на тот же IP чаще, секунд |
| `--max-reports N` | `FTB_MAX_REPORTS_PER_MIN` | `10` | предохранитель: больше отчётов в минуту — отправка встаёт на паузу на 10 минут |
| `--ignore-ports L` | `FTB_IGNORE_PORTS` | пусто | доп. порты назначения через запятую, не считать веером (сверх встроенного списка) |
| — | `FTB_LOG` | пусто | путь к access-логу; пусто — найти по конфигу ноды |

Срок бана и исключения (IP, ID пользователей) задаются в **панели**, в конфиге плагина Torrent Blocker (`blockDuration`, `ignoreLists`). Детектор их не дублирует: нода применяет их к его отчётам так же, как к своим.

Пороги по умолчанию подобраны по замерам на реальном трафике. Между легальным трафиком и торрентом — широкий зазор: самые «веерные» легальные сервисы (P2P-обновления, WebRTC-звонки, игры) за окно дают до ~15 разных портов, торрент-клиент — 140–250. Порог 20 портов сидит в этом зазоре, ложных срабатываний в замерах не было. Ключевую роль играет условие «**И** хосты, **И** порты»: сервис, который бьёт по десяткам адресов, но на узком наборе портов (Windows Update на 7680, звонок на паре UDP-портов), под него не попадает. Если какой-то легальный сервис всё же светит много портов — занеси его порты в `FTB_IGNORE_PORTS`.

### Встроенный список исключённых портов

Веер к разным адресам на этих портах — нормальное поведение, а не торрент, поэтому они не считаются. Список собран по типовому легальному трафику (по каждому порту смотрели реальные адреса назначения и rDNS):

| Порт(ы) | Сервис |
|---|---|
| 22, 53, 80, 443, 8080, 8443 | SSH, DNS, HTTP(S)/QUIC |
| 123, 2002 | синхронизация времени: NTP и Roughtime (`time.cloudflare.com`) |
| 465, 587, 993, 995, 853 | почта и DNS-over-TLS |
| 554, 1935 | потоковое видео: RTSP (камеры), RTMP |
| 3478–3497, 5349, 16384–16403, 19302–19309 | STUN/TURN и RTP — установка и медиа p2p-звонков (WebRTC, мессенджеры, Google Meet) |
| 5222, 5223, 5228 | XMPP и push (в т.ч. Google FCM) |
| 7680 | Windows Update Delivery Optimization — P2P-раздача обновлений (десятки жилых адресов на один порт) |

Осознанно **не** включены порты, веер по которым как раз интересен, — например `3333` и другие stratum-порты майнинг-пулов.

Порты, специфичные для конкретного узла или приложения (в замере такими оказались `1010`, `11223`, `8843` и подобные — трафик отдельных клиентов или неопознанные облачные бэкенды), в общий список не идут: если такой сервис у тебя светит много **разных** портов и цепляется под детектор — добавь его порты в `FTB_IGNORE_PORTS` на этом узле.

## Как отличить от нативного срабатывания

| Где | Нативное | fsnt-torrent-blocker |
|---|---|---|
| Telegram | `Protocol: bittorrent (tcp)` | `Protocol: fsnt-torrent-blocker (tcp)` |
| Панель → отчёты Torrent Blocker | фильтр `Protocol` = `bittorrent` | фильтр `Protocol` = `fsnt-torrent-blocker` |
| Вебхук `torrent_blocker.report` | `xrayReport.outboundTag` = `RW_TB_OUTBOUND_BLOCK` | `xrayReport.protocol` и `outboundTag` = `fsnt-torrent-blocker` |

Цифры находки лежат в `xrayReport.routeTarget`, например `fanout 73 hosts / 58 ports / 86 conns in 60s (tcp 85, udp 1)`. В `destination` — один из пиров.

```bash
curl -fsSL …/install.sh | sudo bash -s -- --uninstall           # настройки остаются

```

## Ограничения

- Бан ставится по IP клиента, как и у штатного плагина. За CGNAT-адресом мобильного оператора может оказаться несколько абонентов.
- Каждая нода решает по своему трафику. Панель узнаёт о бане и шлёт уведомление, но на другие ноды бан не переходит — так устроен плагин. Чтобы отключить нарушителя везде, обрабатывай вебхук `torrent_blocker.report` у себя (например, переводи пользователя в `DISABLED`).
- Детектор ходит во внутренний API ноды (`/internal/webhook`), а не в публичный. После крупных обновлений Remnawave Node сначала прогони `--selftest`.
- Трафик, который не попадает в access-лог, детектор не увидит: при `log.access` = `"none"` работать не с чем.

## Сборка

Детектор вшит в `install.sh` целиком, чтобы установка шла одной командой и без доступа сервера к репозиторию. После правки `fsnt-torrent-blocker.py`:

```bash
./build.sh           # пересобрать install.sh
./build.sh --check   # проверить, что install.sh собран из текущего .py (для CI/хука)
```
